## What I'd Add for Production

Everything above was built with correctness and resilience of the AI layer as the priority. Two entire dimensions were deliberately left out of scope to keep the project focused, and both would be non-negotiable before this ran anywhere real: authentication, and a genuinely concurrent request path.

**Authentication and authorization.** Every route — including `/books/` ingestion and `/health`, which exposes daily AI spend — is reachable by anyone with network access to the service. I'd add an `APIKeyHeader` (or JWT) dependency injected via FastAPI's `Depends()` on each router, checked against a store of issued keys rather than a single shared secret, so keys can be revoked individually. I'd also split scopes: a read scope for search/chat/summarise, and a write scope for the ingest endpoint, since the two have very different blast radii if compromised. Today the rate limiter treats every caller as one shared pool; per-key buckets would come naturally out of the same change, since the key would already be resolved before the limiter is consulted.

**Async and concurrency.** The service layer is entirely synchronous — every route handler is `def`, not `async def`, `BaseProvider` and `EmbeddingsService` both use `httpx.Client` instead of `AsyncClient`, and the cache uses `redis.Redis` instead of `redis.asyncio`. FastAPI papers over this by running sync handlers in a threadpool, so nothing is actually broken, but the app gets none of the benefit of overlapped I/O on exactly the calls that are worth overlapping: the AI-gateway request and the Redis round-trip. I'd convert the request path to `async def` end to end and swap in async clients, which would let a single worker serve far more concurrent chat/RAG requests without adding threads.

That change would also force a fix to a bug that's currently latent rather than triggered: `ChatbotService.conversation` is a plain, unlocked `dict`, and a single module-level `ChatbotService` instance is shared across every request. Two requests hitting the same `conversation_id` at the same time can race on the same read-modify-write append, corrupting that patron's history. I found the rate-limiter's per-service-instance bug and fixed it early; this is the same class of bug in the session-state layer, and it's still there. Fixing it properly means moving conversation state out of process memory and into Redis, keyed by `conversation_id`, with an atomic append rather than a load-mutate-save cycle.

**Multi-worker correctness.** Both of the fixes above matter more than they look because of how this would actually run in production: multiple uvicorn/gunicorn worker processes behind a load balancer, not one. The singleton rate limiter I built solves the "four services, four separate budgets" bug within a single process, but each worker process still gets its own singleton — running four workers silently reintroduces the exact 4x-the-intended-limit bug I already diagnosed once, just at the process level instead of the service level. The same is true of `ChatbotService.conversation`: a patron's follow-up question can land on a different worker than their first message and find no history at all. Both the rate limiter and the chat session store need to live in Redis, not in process memory, before this could run with more than one worker — which it would need to, for real traffic.

**Data layer: Postgres as source of truth, Celery for indexing.** Right now books live only in ChromaDB — the seed script writes titles, authors, years, and blurbs directly into Chroma's metadata, so the vector store is doubling as both the system of record and the search index. That's fine for a fixed seed set, but it doesn't hold up once books (and chapters, which don't exist yet at all) can be created, edited, or retired through the API: Chroma has no real transactional guarantees or relational structure, so there's nowhere to safely store chapter text, track edit history, or enforce that a book's metadata is consistent while it's being re-embedded. I'd move books and chapters into PostgreSQL as the source of truth, and treat ChromaDB purely as a derived, rebuildable index over it. Ingestion would then write to Postgres synchronously (fast, transactional) and enqueue a Celery task to embed and upsert into Chroma asynchronously, instead of making the API request wait on an embedding call the way it effectively does today. Celery beat would run a periodic reconciliation job — comparing a content hash per book/chapter against what's already indexed — so a worker restart, a partial failure, or a direct database edit can't leave Chroma silently out of sync with Postgres.

**Invalidation.** That same content-hash idea is the missing piece for invalidation generally. Today there's no mechanism to know a book's embedding is stale after an edit — you'd have to remember to re-run the seed script. With Postgres as the source of truth, an update to a book or chapter would bump its content hash, which the Celery beat job (or a trigger fired directly from the update endpoint) would use to know it needs re-embedding, delete the old vector by id, upsert the new one, and evict any Redis cache entries keyed on that embedding or on AI responses that were grounded in it — otherwise a patron could get a RAG answer citing a book's old edition after it's been corrected.

**Prompt caching with KV-cache.** Every one of the four AI-calling services rebuilds and resends its full system prompt on every single request — the RAG grounding instructions, the chatbot persona, the classification rubric, and the summarisation instructions are static per service, but the current `BaseProvider.generate()` call sends them as plain text with no caching hint, so the gateway (and whichever model it forwards to) has to recompute attention over that identical prefix every time. Providers that expose prompt/KV-cache (e.g. Anthropic's prompt caching, or a self-hosted vLLM setup with prefix caching) let you mark a static prefix once and reuse its cached KV state across requests, which cuts both latency and cost proportionally to how much of the prompt is the unchanging system/instruction block versus the actual user text. I'd restructure `BaseProvider.generate()` to separate the stable instruction prefix from the per-request variable content and pass the appropriate cache-control markers through to the gateway, since right now that's pure repeated compute being paid for on every chat turn and every search.

**Hybrid retrieval: metadata pre-filtering + semantic re-ranking (also the real fix for titles).** The metadata router handles isolated structured questions well, but it's a binary switch — a question is answered *either* by metadata filtering *or* by semantic search, never both. That breaks down on genuinely compound questions like "planet-themed books published between 2000 and 2023, authored by ...": the year and author are structured constraints, but "planet-themed" is a thematic constraint no regex or exact-match lookup can resolve, and no book *description* is semantically close to "between 2000 and 2023" either. Routing the whole sentence to one strategy or the other necessarily drops half of what was asked. The regexes are also brittle to phrasing on the structured half alone — `"between 2000 and 2023"` matches; `"2000-2023"` or `"all the books"` instead of `"all books"` do not — because hand-writing a pattern for every phrasing of "between," "authored by," or "title that includes" doesn't scale the way it did for the one narrow year-range bug this was originally built to fix.

The standard RAG pattern for this is **metadata pre-filtering + semantic re-ranking**: extract every structured constraint from the question (year, genre, author, title), apply them as a hard filter over the catalogue first, then run semantic similarity *only on the remaining free-text/thematic residual* ("planet-themed") against whatever books survive the filter, instead of embedding the whole compound sentence. ChromaDB supports this natively — `collection.query()` accepts a `where` clause alongside the query embedding, so a single call can do "vector-similar to X, restricted to books matching this metadata filter" without first pulling the whole catalogue into Python the way `get_all_books()` does today. That change alone would also make the metadata path scale past a small seed catalogue, since right now every structured query fetches every book in the collection.

The part that doesn't scale as hand-written regex is the extraction — reliably splitting a sentence into "structured part" vs. "semantic residual part" across arbitrary phrasing. I'd replace the regex parsing in `metadata_filter.py` with a small structured-output AI call: a cheap, low-`max_tokens` request that returns `{year_range, genre, author, title, semantic_residual}` as JSON, given the question and the catalogue's real genre/author/title values (the same inputs `build_filter_spec` already gathers). This is strictly more robust to phrasing than any regex set, and it produces the semantic residual as a byproduct — the exact text to embed and re-rank within the filtered subset, with no separate extraction step needed for it.

This is also the actual fix for the title-matching problem, and a better one than the title-specific approach considered earlier (matching a known title against a whitelist of intent phrases like "tell me about X"). That approach only recognises the phrasings on the whitelist and still risks a bare word colliding with an unrelated question. Once title is just one more field the extraction call resolves — the same way it resolves year, genre, and author — "tell me about Dune," "what's Dune's plot," and "the book called Dune" are all handled identically and correctly, with no phrasing list to maintain.

To keep this from adding cost to every request, I'd keep the current cheap regex/keyword check (`looks_like_metadata_query`) as a first-pass gate exactly as it is today — it costs nothing and already catches the obvious cases. Only when it fires (or a lightweight, uncached check turns up a known title substring) would the extraction AI call run, so ordinary semantic questions never pay for it. The extraction call also needs its own fallback: if it fails or returns malformed JSON, fall back to plain semantic search on the original question rather than erroring out, the same compensating-transaction pattern already used elsewhere for AI-call failures. In rough shape:

```python
def _retrieve_relevant_books(self, question):
    if looks_like_structured_query(question):          # cheap regex gate, unchanged
        try:
            plan = self._extract_query_plan(question)   # NEW: small structured-output AI call
        except AIProviderException:
            plan = None                                  # graceful fallback, not an error

        if plan is not None:
            where = build_chroma_where(plan)             # year/genre/author/title -> Chroma `where`
            if plan["semantic_residual"]:
                query_vector = self.embedding_service.embed(plan["semantic_residual"])
                candidates = self.vector_store.search_books(query_vector, top_k=self.rag_top_k, where=where)
                relevant = [b for b in candidates if b["similarity"] >= self.relevance_threshold]
            else:
                relevant = self.vector_store.filter_books(where)   # pure structured match, no embedding
            return relevant, describe_no_match(plan)
```

This is a meaningfully bigger feature than the year-range fix — it touches the vector store's filtering API, adds an extraction step with its own failure mode and rate-limiter cost, and changes how context gets assembled for compound results. Given the original bug report was specifically about year filtering, I scoped that narrowly and am treating this as a follow-up rather than folding it into the current fix.

**Smaller gaps.** A few other things I'd fix given more time, roughly in order of how much they'd embarrass me in a real incident: the global exception handler currently returns `f"Internal server error: {type(exc).__name__}: {exc}"` straight to the client, leaking implementation details that should stay in the logs; `/health` only reports request counts and cost, not whether Redis, ChromaDB, or the AI gateway are actually reachable, so it can report healthy while every dependency is down; there's no Dockerfile for the app itself (only `docker-compose.yml` for Redis), so "production-grade" currently stops at the process boundary; and the 324 tests are all unit tests against services and providers with mocks — there's no `TestClient`-based integration test exercising a router, the exception handler, or the auth layer once it exists, which is exactly the seam where the Pydantic `year` coercion bug from earlier slipped through.
