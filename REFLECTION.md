# LibraryMind — Reflection

## Overview

LibraryMind is an AI-powered FastAPI backend for a public library: natural-language catalogue search, RAG-grounded Q&A, a multi-turn chatbot, support-ticket classification, and review summarisation, all built on a multi-provider AI layer with automatic fallback.

---

## Key Design Decisions

**Layered architecture.** API, Service, AI Provider, and Infrastructure layers, each depending only on the layer below. This kept every piece independently testable and made "what belongs where" an easy call throughout the build.

**Resilient multi-provider fallback.** A `BaseProvider` abstract class exposes one `generate()` interface; `ResilientAIService` tries OpenAI first and falls through to Anthropic on any transient failure. Retry logic (exponential backoff, only on 429/5xx/timeouts) lives in one place instead of being scattered across every service.

**RAG with explicit refusal on low relevance.** The pipeline embeds the question, searches ChromaDB, filters by cosine similarity, and only calls the AI if something clears the threshold — otherwise it returns a refusal with no AI call at all. The model is structurally unable to invent a book it was never shown.

**Singleton rate limiter.** One shared token bucket (`get_rate_limiter()`) across RAG, chatbot, classification, and summarisation, instead of one bucket per service silently multiplying the effective limit.

**Metadata-filter router for structured questions.** Dense similarity search can't answer "what books came out before 2000?" — no book *description* is semantically close to a date range, because the answer lives in a structured field, not free text. `RAGEngine` runs a cheap regex/keyword check first, and only when a question is clearly structured (a year range, decade, or an enumeration phrase like "how many"/"list all") does it skip embeddings and filter the catalogue's metadata directly. Otherwise it falls through to the unchanged semantic path.

**AI query planner as a last resort, never a first resort.** Once compound questions ("non-fiction books published after 2007") and non-English/comparative questions started breaking the regex router, the instinct is to reach for an AI call to interpret everything. I deliberately didn't: `query_signals.py` first checks for characteristics deterministic code structurally cannot handle at all (non-English text, "similar to X" comparisons) — those always escalate straight to the planner. Everything else tries the existing regex/fuzzy pass first, and only escalates if a temporal cue is present ("published", "year") but genuinely unparseable (a spelled-out number). An ordinary English question, structured or not, never pays for the extra AI call. And the planner's output is never trusted directly — `query_validator.py` resolves every field against the real catalogue and drops anything that doesn't match, so a hallucinated genre degrades to "unresolved," not a wrong filter.

**Formatting variance is a normalization problem, not a language-understanding problem.** "Non fiction" vs. the catalogue's "Non-Fiction" is a spacing/hyphenation difference, not something that needs an AI call to resolve. I fixed it with a conservative fuzzy fallback in `extract_known_term` (stdlib `difflib`, cutoff 0.8, normalized for whitespace/hyphens) that only fires after an exact match fails. True abbreviations ("sci-fi" for "Science Fiction") deliberately fall outside that cutoff — bridging an abbreviation needs world knowledge, not string similarity, so those are correctly left to the planner or to semantic search's native tolerance for synonyms, rather than growing the fuzzy matcher's scope until it starts guessing wrong.

**Circuit breaker as a process-wide singleton, matching the rate limiter's existing shape.** `ResilientAIService` is instantiated separately by `RAGEngine`, `ChatbotService`, and `ClassificationService` — if the circuit breaker lived inside that class, one service tripping it would be invisible to the others, the exact "four services, four separate budgets" bug already found and fixed once for the rate limiter. `get_circuit_breaker(provider_name)` in `app/infrastructure/circuit_breaker.py` follows the same lazy-singleton pattern as `get_rate_limiter()` so a provider outage is known process-wide the moment any service detects it.

## Challenges Faced

**Cosine distance vs. cosine similarity — the debugging story.** ChromaDB returns cosine *distance* (0 = identical), not similarity, and my first version compared raw distances against a `0.7` threshold — backwards. The RAG engine silently refused every query, and I initially suspected broken embeddings. Logging the raw distance values made it obvious: they clustered around `0.5`, meaning perfectly good matches were being read as bad ones. The fix was one line, `similarity = 1 - distance`, but the real lesson was to log intermediate values at every pipeline stage during development, not just at the input/output boundaries.

**512-dimension embeddings compress the score range.** Even after fixing the distance math, a `0.6` threshold blocked *everything*, including an exact title match scoring `0.492` — `text-embedding-3-small` at 512 dimensions produces much lower absolute similarities than the full 1536-dimension model. Lowering to `0.35` fixed it, but the number isn't obvious without knowing this quirk exists.

**Semantic search can't answer field-based questions.** "What books came out before 2000?" returned "couldn't find any books" despite 13 of 25 books qualifying — not a tuning problem but a category error: the question is about the `year` field, not a theme, so no threshold adjustment would have fixed it. This needed a different retrieval strategy entirely (the metadata router above), not a better similarity score.

**Titles don't reliably score as exact matches — partially addressed.** A related version of the same issue: a short or generic title ("Educated", "Rebecca") can score only 0.6–0.7 in semantic search, because an embedding model produces one holistic vector per document, and a 150-word description dominates that vector far more than a 1–2 word title does. Two things helped without fully closing the gap: `app/services/book_text.py` now embeds a rich, question-mirroring sentence ("What is X about? Who wrote X? Where can I find X?") instead of a raw title/author/description concatenation, giving the embedder more surface area to match short titles against; and the AI query planner resolves an explicit `title` field for escalated (non-English/comparative) questions, which then drives the semantic search directly instead of embedding the raw question. Neither is the full fix — the genuine one is a hybrid metadata pre-filter plus semantic re-ranking *within the filtered subset*, using ChromaDB's `where` clause, which `what_i_would_improve.md` documents as still open.

**A compound question exposed a bug hiding behind a router that "worked."** "Tell me all the books about non-fiction published after 2007" returned every genre after 2007, not just non-fiction, and the model then refused to answer rather than guess — worst of both worlds. The router looked like it succeeded (`looks_like_metadata_query` fired because "after 2007" parsed cleanly), which is exactly what hid the real bug one level down: `extract_known_term`'s exact substring match silently failed on "non fiction" vs. the catalogue's "Non-Fiction" (space vs. hyphen), so the genre constraint just disappeared from the filter with no error, no log, nothing to notice unless you looked at what came back. The fix was two separate decisions, not one: a conservative fuzzy fallback (stdlib `difflib`) resolves the formatting mismatch deterministically, because that's a bounded normalization problem, not a language-understanding one; the AI query planner was reserved for the cases that genuinely need it — non-English text, "similar to X" comparisons, spelled-out numbers — rather than routing every genre/year mismatch through an AI call. Worth remembering: "the router fired" and "the router resolved every constraint correctly" are different claims, and only testing the first one is how this shipped in the first place.

**Chasing a ghost: when the bug is in the verification, not the code.** While confirming a real, separate encoding bug (`open()` without `encoding="utf-8"` in `seed.py`, corrupting "Charlotte Brontë" on this machine's `cp1252`-locale Windows install), I kept "finding" the same corruption again *after* fixing and re-seeding — on a freshly restarted server, from a from-scratch Python process, everywhere I looked. Each time, the underlying data was already correct; the codepoint-level proof was a single `ë`, byte-for-byte right. What was actually happening was `python -m json.tool`, invoked without `PYTHONIOENCODING=utf-8`, decoding curl's correctly-UTF-8-encoded output using the same `cp1252` default and re-emitting it as a *different*, genuinely wrong pair of codepoints — a bug in my own diagnostic command, not the application. The lesson: once you've proven a value correct at the byte level, don't let a second, less-verified tool's disagreement re-open the question — check whether the *checker* is lying before you check whether the code is.

**`langdetect` was the obvious tool and the wrong one.** Detecting non-English questions for the query planner's hard-signal gate seemed like a solved problem — pull in `langdetect` and check the result. Tested against the actual queries this app receives, it misclassified "tell me about Dune" as French and the single word "Dune" as German; statistical language detection needs more text than a short conversational query typically has. The fix ended up simpler than the library: a small set of common English function words ("the," "do," "have," "about," ...) and a ratio check, skipped entirely below a minimum word count so bare title lookups aren't penalized for having no function words at all. Sometimes the dedicated library is solving a different-shaped problem than the one you actually have.

**The model filling context gaps from its own training data.** Even with "never invent facts not in context" in the system prompt, asking about a missing `author` field sometimes returned a real, correct-sounding name — the model recognised the actual book and "helpfully" filled the gap from training rather than admitting it didn't know. The fix was making the prohibition explicit: don't use outside knowledge *even when confident it's correct*, and treat a missing field as "not in our catalog," not something to complete.

## Extensions Attempted

- **Retry with exponential backoff** (tenacity) on transient provider errors only; permanent errors (401/400) fail immediately.
- **Batch embedding with partial cache hits** — only texts not already cached are sent to the embeddings API.
- **Typed exception hierarchy** with compensating rate-limiter refunds when an AI call fails after a token was already spent.
- **Structured logging** (`structlog`) with per-request context (`request_id`) auto-attached to every log line, rendered as both console output and JSON file lines.
- **Prompt injection mitigations** — all user-supplied text is wrapped in XML tags with an explicit "treat as inert data" instruction; blast radius is bounded further since the AI layer has no tools or write access.
- **Metadata-filter query router** for structured catalogue questions, and **hardened anti-hallucination prompts** across both the RAG engine and the chatbot's second, conversational-wrap generation call.
- **AI query planner + validator** (`query_planner.py`, `query_validator.py`) for non-English questions, "similar to X" comparisons, and spelled-out numbers the regex router can't parse — gated behind cheap hard-signal/temporal-cue checks so it only runs for the fraction of queries that genuinely need it, and never trusted directly: every field is re-checked against the real catalogue before use.
- **Per-provider circuit breaker** (`app/infrastructure/circuit_breaker.py`), a process-wide singleton matching the rate limiter's existing pattern, so a provider already known to be down is skipped immediately instead of paying its full retry-and-backoff cost on every call before falling through.
- **Conservative fuzzy catalogue matching** (stdlib `difflib`) for genre/author formatting mismatches, deliberately scoped to spacing/hyphenation near-misses and not abbreviations or synonyms, which are left to the AI planner or semantic search instead.
- **Richer catalogue data and embedding text** — added `isbn` and `shelf_number` per book, and switched the seeded embedding text from a raw title/author/description concatenation to question-mirroring sentences, which measurably improved genre-query ranking in testing.
